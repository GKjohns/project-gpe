Project GPE (Graphical Proof Explorer) · storyboard for v1 (paper-only, web app)

Each frame is a moment in the core loop: run the pipeline on a paper → open the map → read a node → ask the chat → read the friction report. Mocked on Nuxt UI 4's dashboard template and primitives so each frame maps 1:1 onto what the sprints write. Data is the real ETH paper's section and label structure from openai/math; semantic names, explanations and Lean helper names are illustrative of pipeline output.

New paper: point it at a source

Sprint 2

00b

Run page: watch the pipeline work

Sprints 2–4, 4b

The pipeline is one function with a step per stage (fetch, chunk, outline, extract, resolve, critique, annotate, classify, finalize; the stepper groups them to seven), and the LLM-heavy stages fan out into one step per claim (extract) and one step per dependency level (annotate), so no single serverless invocation runs longer than one model call. Critique can pause the run on a review queue (accept/reject per proposed fix) before any prose is written. The structure step has two methods, picked on the form: pipeline (one whole-paper outline call, then a critique) or agent (a Claude Agent SDK run inside a Vercel Sandbox that reads the paper its own way; the Inngest step waits on its finish event and the log shows its tool-call trace). Same outline contract out of both; everything downstream is identical. Each step writes a row to run_events; the page polls GET /api/runs/:id every two seconds. Failed steps retry by themselves; the Retry stage button re-sends from a stage with the earlier stages' outputs reused, which is how a prompt tweak gets re-run cheaply. Click Jump to finished to see the end state.

On rails: UStepper (stages), two UCards, the log as a plain list (a UTimeline is overkill). Route /papers/[slug]/run. Server: server/pipeline/ingest.ts is written against a small StepRunner interface (step.run, step.waitForEvent); every step upserts runs.progress and appends run_events. In dev the LocalRunner executes the steps in the Nuxt server process right after the form POST returns, so npm run dev is plain nuxt dev. In prod the same function runs under Inngest (InngestRunner wraps Inngest's step, served at /api/inngest in the standard way); wiring it is a one-sprint task, and the pipeline code does not change.

02b

Graph view: the proof as a DAG

Sprint 6

Toggle Graph in the navbar and the center panel becomes the dependency DAG: every paper statement is a node, every "uses" edge is drawn, layered so the main theorem sits at the top and the things it rests on fan out below it. The tree sidebar collapses to give the graph room; the right panel shows the selected node's page in compact form. Click any node: it gets focus, everything it depends on (down) and everything that depends on it (up) stays lit, the rest dims. That lit subgraph is the hierarchical perspective on a lemma. Controls: Whole paper / Focus (focus hides the dimmed nodes and re-lays out), Show claims (in-proof claims appear under their parent), color by classification or by section. Pan by scrolling; fit-to-width button. This is layered (Sugiyama-style) layout, not force-directed; proofs are DAGs with a clear direction and should read top-down.

Off rails, on purpose: Nuxt UI has no graph primitive, so ProofGraph.vue is a custom component: @dagrejs/dagre for the layered layout (≤ a few hundred nodes; no WebGL, no force sim) rendered to inline SVG with Vue, pan/zoom via a transform, nodes as foreignObject cards so the badges match the rest of the app. The navbar toggles, mode and color controls stay UTabs/UCheckbox/UButton. Route state in the query (?view=graph&mode=focus) so a graph view is shareable like a node. This is the one custom component in v1.

Decisions this storyboard commits to (push back here)

  • Tree for structure, DAG for dependencies, both first-class. The sidebar tree is the paper's own hierarchy (section → statement → in-proof claim → Lean helper) via UTree. The center panel toggles between the node page and the dependency graph (frame 02b), a layered DAG with focus mode. The graph is the one custom component in v1 and is built before the friction report, which is demoted to a small late sprint.
  • Chat is a panel, not a page. Third resizable dashboard panel so answers can drive the center pane. No chat history or persistence in v1.
  • Nothing command-line. Ingestion is a form; the run has a page; the corpus is a page. The only terminal command is npm run dev.
  • Two structure methods, compared. The proof-breakdown step runs either as fixed pipeline calls or as a Claude Agent SDK agent in a Vercel Sandbox; both write the same outline and the corpus page compares them per paper. Default is decided by the data, possibly by paper size.
  • Serverless-shaped pipeline, Inngest in prod, mocked in dev. The pipeline is written against a StepRunner interface: one step.run per stage, fan-out per claim and per dependency level, waitForEvent for the review queue and the agent. Dev runs it in-process; prod runs it under Inngest. No step outlives a single model call, so it deploys to Vercel unchanged once the Inngest runner is wired.
  • Postgres from day one, Supabase later. Drizzle schema (papers, sources, runs, run_events, stage_outputs, review_items) over PGlite locally (file-backed Postgres in .data/pg/, zero install) and over DATABASE_URL when set. Going live is a connection string plus RLS, not a rewrite. The digest is one jsonb per paper; at a few hundred nodes a paper, no separate nodes table.
  • Friction is a data contract, not a feature, in v1. Friction items are stored on nodes and shown on the node page; the report page is a plain table built last.
  • Math rendering: KaTeX for statement_paper (LaTeX from the source). Everything else is plain text/markdown.
  • Kinds extended: the brief's kind union gains corollary; the ETH paper has five.
